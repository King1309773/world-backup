# 快照停顿优化：1.0.0 基准调查

日期：2026-10-16。被测源码：`afedd9908eb04a27c8d85f1617f1452023b1ec58`（当前代码与 v1.0.0 标签一致）。此次仅新增诊断工具和报告，尚未修改运行时快照算法。

## 方法与适用范围

使用项目 Temurin Java 8、Windows、E: NTFS 本地磁盘，在 `build/performance/baseline-<随机值>` 中生成独立模拟存档。机器枚举的两块物理磁盘均为 NVMe SSD；本次未将 E: 精确映射到具体型号。测试直接调用生产 `NioSnapshotStager.stage`，沿用路径检查、空间预检和文件复制。通过可注入的 FileCopier 对私有生产 copyFile 方法计时；反射调用本身包含在该计时中。

每个场景连续运行三次。原文件刚生成，操作系统缓存和防病毒扫描状态没有隔离，结果属于本机缓存条件下的基线，不能用于预测 HDD、冷缓存、实际整合包的绝对停顿。

`stage_ms` 是 staging 调用耗时；`copy_ms` 包含源/目标文件打开、64 KiB 缓冲复制、关闭与目标修改时间设置；差值包含扫描、排序、路径检查、文件属性复检、目录创建和任务管理等，不能将差值全部视为可删除的浪费。`scan_probe_ms` 是 stage 完成后额外执行一次 inspectTree 的诊断耗时，未计入 stage。`cleanup_ms` 单独记录，未计入 stage。

这里不包含 Minecraft 保存/flush、服务器与线程调度、恢复保存后的再次保存、后台散列/归档校验，也不测量真实渲染帧率。因此不能把 stage 等同于实际游戏完整停顿。

## 已确认的调用路径与后续假设

- `BackupCoordinator.begin` 在服务器线程执行 prepare，然后等待 staging 完成，恢复世界后才提交后台归档。
- `prepareInitialized` 依次保存世界、玩家、区块并 flush 唯一保存处理器。
- `stage` 在复制前清理旧临时目录并完整检查目录树，再为每个文件在复制前后验证身份、属性及路径。
- `requireContainedRealPath` 每次执行两次真实路径解析；这是小文件场景需要进一步单独计时的候选来源，尚不能据此移除安全检查。
- `restoreWorldFlagsAndSave` 会在恢复标志后再次保存世界，该阶段需要在真实游戏中计时；模拟目录无法测量其成本。

后续优化应先保留一致时间点、取消/超时、路径约束与失败回滚，再比较同一数据集上的性能。暂不引入实时世界硬链接、跨 tick 复制活动文件或平台专用卷影快照。

## 复现

项目已编译后，从仓库执行：

```powershell
.\tools\performance\run-baseline.ps1
```

工具最多同时保留一个模拟源场景和其快照，峰值约 2 GiB，输出逐轮数据；正常结束后删除自己生成的 source/staging 树。若进程被强制终止，可能留下该工具专属的 baseline-<随机值> 目录，需先确认没有基准进程使用它再处理。
